# 캐시 핸드레인지 페이지 설계

## 목표

100BB 6-max 캐시 프리플랍 데이터(`gto-cache-preflop-chart.json`)를 별도 페이지에서 조회한다. 사용자는 전체 13×13 차트를 보거나, 차트를 끄고 자신의 핸드와 상황을 입력해 액션별 빈도를 확인할 수 있다. 새 데이터의 로딩 실패는 기존 페이지에 영향을 주지 않는다.

## 범위

- 메뉴 이름: `캐시 핸드레인지`
- 데이터에 포함된 22개 시나리오 전체 지원
- 100BB 전용이므로 기존 스택 탭은 표시하지 않음
- 퀴즈, 통계, 사용자 저장 및 동기화 기능은 추가하지 않음

## 페이지 구조

페이지는 자체 데이터 로더를 사용한다. 앱 시작이나 다른 페이지에서는 캐시 JSON을 요청하지 않고, `캐시 핸드레인지` 페이지가 마운트될 때만 요청한다. 로딩, 오류, 데이터 형식 오류는 페이지 내부에서만 표시한다.

입력 항목은 다음과 같다.

- 내 포지션: UTG, HJ, CO, BTN, SB, BB 중 선택
- 앞선 액션: 없음, 오픈 있음, SB 림프, BB 레이즈(SB 림프 후)
- 상대 오픈 포지션: `오픈 있음`일 때 가능한 앞 포지션만 선택
- 내 핸드: `AA`, `AKs`, `AKo` 형식의 직접 입력
- 차트 표시 스위치

선택한 내 포지션에 성립하지 않는 앞선 액션과 상대 포지션은 선택지에서 제외한다. 일반 RFI와 오픈 대응뿐 아니라 다음 블라인드 특수 상황도 제공한다.

- BB vs SB limp
- BB vs SB raise
- SB vs BB raise after limp

## 표시 동작

공통 상황 입력은 차트 표시 여부와 관계없이 유지한다.

### 차트 켜짐

선택한 시나리오의 169개 핸드를 13×13 그리드로 표시한다. 액션이 혼합된 셀은 각 액션 색상을 빈도 비율만큼 분할한다. 셀의 상세 정보에는 모든 0% 초과 액션과 빈도를 표시한다. 유효한 핸드가 입력되어 있으면 해당 셀을 강조한다.

기존 `RangeGrid`는 단일 액션 색상을 전제로 하므로 변경하지 않는다. 캐시 페이지에 필요한 혼합 빈도 그리드를 별도 컴포넌트로 두어 기존 차트 동작과 스타일 회귀 위험을 피한다.

### 차트 꺼짐

유효한 핸드가 입력되면 해당 핸드의 0% 초과 액션과 빈도를 모두 표시한다. 가장 높은 빈도의 액션을 주 액션으로 표시하며, 최고 빈도가 같으면 동률 액션을 모두 표시한다.

핸드 입력은 공백과 대소문자를 정규화한 뒤 169개 표기만 허용한다. 잘못된 입력은 결과 대신 간단한 형식 안내를 표시한다.

## 액션 표현

원본 액션 키는 데이터의 베팅 크기를 보존해 사용자용 문구로 변환한다.

- `raise_2.5` → `2.5BB 레이즈`
- `call` → `콜`
- `fold` → `폴드`
- `check` → `체크`
- `all_in_100` → `100BB 올인`

다른 `raise_N` 값도 같은 규칙으로 표시한다. 빈도 0% 액션은 결과와 상세 정보에서 숨긴다.

## 데이터 선택과 검증

JSON의 `scenarios` 배열을 런타임에 그대로 사용한다. 별도 변환 파일은 만들지 않는다. 시나리오는 `position`과 `actionHistory`를 기준으로 선택한다.

페이지가 사용하는 경계에서 최소 데이터 형식을 검증한다.

- `scenarios`가 배열인지 확인
- 각 시나리오에 식별자, 포지션, 액션 히스토리, 핸드 데이터가 있는지 확인
- 선택한 시나리오나 핸드가 없을 때 페이지 내부 오류 표시

## 암호화와 배포

평문 `public/gto-cache-preflop-chart.json`은 `.gitignore`에 유지하고 저장소에는 `public/gto-cache-preflop-chart.json.enc`만 커밋한다.

기존 `DATA_KEY`와 OpenSSL AES-256-CBC/PBKDF2 방식을 그대로 사용한다. `npm run encrypt`와 `npm run decrypt`는 기존 GTO JSON과 새 캐시 JSON을 모두 처리한다. Vercel의 기존 `build:vercel` 흐름은 `decrypt` 후 Vite 빌드를 실행하므로 별도 배포 단계는 추가하지 않는다.

## 테스트와 완료 조건

최소 단위 테스트로 다음을 확인한다.

- 핸드 입력 정규화 및 169개 표기 검증
- 내 포지션과 앞선 액션에 맞는 시나리오 선택
- 혼합 빈도에서 0% 제거 및 최고 빈도 액션 계산

완료 시 전체 테스트, TypeScript/LSP 진단, 프로덕션 빌드를 실행한다. 기존 페이지에서는 새 JSON 네트워크 요청이 발생하지 않아야 하고, 새 JSON의 로딩 실패가 기존 앱 데이터 로딩을 막지 않아야 한다.
